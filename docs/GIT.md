# Ветки, окружения и что не попадает в репозиторий

Короткий документ на один вопрос: куда коммитить и что коммитить нельзя.
Обоснование — в `docs/DECISIONS.md`, D-043, D-057 и D-058.

## Ветки

| ветка | что это | кто её трогает |
|---|---|---|
| `main` | прод. То, чем пользуются | только слияние из `develop` |
| `develop` | общая проверка перед продом | слияние из фича-веток |
| `feature/<что-делаем>` | одна задача | тот, кто её делает |

Порядок один: фича-ветка → показ **из неё же** → согласие человека → `develop` →
`main`. И это не договорённость, а проверка (D-059, D-069):

- **в `main` сливается только `develop`.** Попытка слить туда что-то ещё
  останавливается хуком с объяснением, каким путём идти;
- **прямой коммит в `main` и в `develop` запрещён**: обе ветки собираются
  слиянием, и коммит мимо ветки задачи обходит правило молча. Запрет на
  `develop` появился не из осторожности: в открытую половину провалились —
  коммит ушёл прямо туда (D-069);
- **в `develop` сливаются только ветки задач**, не `main` и не он сам;
- **слияние в общую ветку требует согласия человека.** Хук не умеет отличить
  одобренное от неодобренного, поэтому согласие передаётся явно переменной
  `APPROVED_BY`. Подставлять туда что попало, не спросив, — то же самое, что
  слить без спроса.

```bash
git switch develop
git switch -c feature/pdf-page-breaks
# … работа, локальные запуски, тесты …
pnpm run dev                 # ← показываем работу отсюда: http://<ip>:4291
# … человек посмотрел и одобрил …
git switch develop
APPROVED_BY="рюфус" git merge --no-ff feature/pdf-page-breaks
# ← контур develop пересобрался сам, проверяем на 4092
git switch main
APPROVED_BY="рюфус" git merge --no-ff develop
# ← прод пересобрался сам, проверяем на 4090
```

Показать работу — значит дать ссылку **на свою ветку**. Слить в `develop` и
показать `develop` — это уже не показ, а свершившийся факт: решение, которое
принимает человек, у него отобрали.

## После слияния контур пересобирается сам

Хук `post-merge` пересобирает и перезапускает то окружение, которому
принадлежит ветка: слияние в `main` — это выкатка прода, слияние в `develop` —
обновление окружения проверки. Раньше это были два шага, и второй забывался:
код в ветке новый, а в докере крутится вчерашний образ.

Слияние в фича-ветку не пересобирает ничего — они в докер не уезжают.

Пропустить пересборку, когда сливают несколько веток подряд:

```bash
FATOFF_NO_REDEPLOY=1 git merge --no-ff feature/…
```

Пересборка идёт **после** записи слияния. Если она не удалась, слияние уже в
истории, а контур остался на прежнем образе — об этом пишется прямо, вместе с
командой, которой повторить.

В репозитории выключено ускоренное слияние (`merge.ff=false`): без коммита
слияния хуки не запускаются вовсе, и правило можно было бы обойти, не заметив
этого.

## Окружения

| ветка | порт | база | как поднимается |
|---|---|---|---|
| `main` | 4090 | `fatoff` в `fatoff-postgresql` (5482) | `pnpm db:up && pnpm docker:up` |
| `develop` | 4092 | `fatoff` в `fatoff-develop-postgresql` (5483) | `pnpm develop:up` |
| `feature/*` | 4290 API, 4291 фронт | `fatoff_dev` в базе develop | `pnpm run dev` |

У прода и develop свои контейнеры, свои тома и свои сети. Общий у них только
образ, собираемый из одного `Dockerfile`. Фича-ветки в докер не уезжают вовсе:
их запускают и проверяют локально.

Тесты ходят в базу develop и заводят там свои базы `fatoff_test_<файл>`.
Прод не делит с разработкой даже процесс базы.

## Что нельзя коммитить

Репозиторий публичный, а сервис работает с дневником питания и историей
здоровья живого человека. Поэтому в него не едут:

- **секреты** — `.env`, `secrets/`, ключи, токены, пароли;
- **чужие данные** — выгрузка Apple Health, дампы базы, собранные выгрузки;
- **опознающие следы** — почты, имена, живые замеры тела. В документах и тестах
  стоят условные значения, и менять их на настоящие нельзя.

Первое закрывает `.gitignore`. Второе и третье — проверка
`scripts/scan-secrets.mjs`, которую зовёт хук перед каждым коммитом. Она
смотрит и на пути, и на содержимое: почта, ключ от тридцати двух
шестнадцатеричных знаков, JWT, пароль значением, строка подключения с паролем,
файл крупнее двух мегабайт.

```bash
git config core.hooksPath .githooks   # один раз в новом клоне
pnpm scan                             # проверить весь репозиторий руками
pnpm scan:test                        # тесты самой проверки
```

Строку, безопасную по существу, можно пометить комментарием
`scan-secrets: allow` — на ней самой или на одной из двух строк выше. Рядом
должно быть написано, почему она безопасна. Сейчас так помечены только образцы
внутри тестов самой проверки. Пары OAuth приложения YAZIO в репозитории больше
нет — она приходит из `.env` (D-086).

## GitHub

Репозиторий лежит на GitHub (`origin`) со всей историей. Отправляются `main`,
`develop` и ветки задач — обычным `git push`; порядок слияний от этого не
меняется, хуки работают локально, как и раньше.

Регулярное выражение не узнаёт человека по числам: вес, рост, норма белка,
выведенная из веса, проходят мимо сканера. Поэтому всё, что пишется о ней в
документах и тестах, пишется условными значениями, а свои опознаватели — имя,
домены, почты — перечислены в `.scan-local.json`, который сам в git не уезжает.

Автор коммитов — адрес владельца в `git config user.email` этого репозитория:
GitHub связывает коммит с профилем только по адресу. История однажды
переписывалась (D-086); резервная копия до переписывания — bundle вне
репозитория.

`git commit --no-verify` обходит хук. Это осознанное решение и повод объяснить
его в сообщении коммита, а не привычка.
