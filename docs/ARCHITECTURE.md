# FatOff — архитектура и план реализации

Локальный сервис: выгружает аккаунт YAZIO в свою базу, показывает состояние в
браузере и собирает из накопленного файлы в форматах, пригодных для передачи
ИИ на анализ.

Документ описывает, что строится, из чего, в каком порядке и как проверяется.
Журнал развилок — `DECISIONS.md`. Разобранное API YAZIO — `YAZIO-API.md`.
Загрузка Apple Health — `APPLE-HEALTH.md`. День целиком и генератор режима —
`PLANNER-ARCHITECTURE.md`, с разбором норм в `ANALYSIS-NUTRITION.md`.

---

## 1. Что должен уметь сервис

| # | Возможность | Проверяется |
|---|---|---|
| 1 | Добавить аккаунт YAZIO по почте и паролю **или по готовому токену** (вход через Apple ID), убедиться, что вход проходит | UI: карточка аккаунта появляется со статусом «вход выполнен» |
| 2 | Выгрузить всю историю аккаунта в базу сервиса | первый синк тянет от даты регистрации до сегодня |
| 3 | Досинхронизировать только изменившееся | повторный синк за тот же период укладывается в единицы запросов |
| 4 | Показывать ход выгрузки и её итог | прогресс по фазам, счётчик дней, список предупреждений |
| 5 | Собрать файл за произвольный период в CSV, JSON, TOON, Markdown | файл скачивается из UI |
| 6 | Держать несколько аккаунтов независимо | данные и файлы аккаунтов не пересекаются |
| 7 | Работать локально одной командой | `docker compose up -d` |

Конечный потребитель выгрузки — не человек, а языковая модель: файл должен быть
полным, компактным и однозначным в единицах измерения.

## 2. Стек

Тот же, на котором сделаны `dynamic-competitor` и `family-calendar`:

- **Монорепо**: pnpm 10 + Turborepo, Node 22.22.0
- **Backend**: NestJS 11 (Express, CommonJS), MikroORM 6, PostgreSQL 17, Pino, Zod для окружения, Vitest
- **Frontend**: Nuxt 4 в режиме SPA, свой CSS, без библиотеки компонентов
- **Общие типы**: пакет `@fatoff/contracts`
- **Запуск**: Docker Compose — контейнер приложения и контейнер базы

Слои backend — как в DC: `Controller → Process/Service → Repository → Entity`.
Файлы в kebab-case, идентификаторы в БД в snake_case, комментарии по-русски.

Порты (заняты соседними проектами 4080/5480/5481, поэтому свои):

| что | порт |
|---|---|
| приложение (API + собранный фронт) | 4090 |
| Nuxt в режиме разработки | 4091 |
| PostgreSQL | 5482 |

Имена: пакеты `@fatoff/*`, база `fatoff`, пользователь `fatoff`, сеть `fatoff-net`,
контейнеры `fatoff-app` и `fatoff-postgresql`.

## 3. Устройство

```
                          браузер (Nuxt SPA)
                                 │  /api/*, cookie-сессия
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│  NestJS                                                          │
│                                                                  │
│  auth ──── вход в сервис по одному паролю                        │
│  accounts ─ аккаунты YAZIO, шифрование учётных данных            │
│  yazio ──── клиент API: токены, ретраи, лимит параллельности     │
│  sync ───── планировщик дней и движок выгрузки                   │
│  analytics ─ сводки для дашборда                                 │
│  exports ── таблицы → CSV / JSON / TOON / Markdown → файл        │
│  schedule ─ ночная автосинхронизация                             │
└──────────────┬──────────────────────────────┬────────────────────┘
               │                              │
        PostgreSQL (сырьё + ряды)      storage/exports (файлы)
               ▲
               │ HTTPS
        yzapi.yazio.com/v9
```

### 3.1 Ключевое решение: сырьё — источник правды

Сервис хранит **ответы YAZIO как есть** (jsonb, по дню и по аккаунту), а все
таблицы выгрузки считает из них **чистыми функциями в момент сборки файла**.

Что это даёт:

- изменилась логика подсчёта — пересобрали файл, не трогая сеть;
- экспорт детерминирован и мгновенен: он не ходит в YAZIO вообще;
- вся арифметика оказывается в чистых функциях, а они тестируются без базы и
  без сети — это и есть основной слой тестов;
- если YAZIO завтра закроет API, накопленное остаётся у пользователя.

Цена — денормализованное хранение. Для четырёх лет истории это порядка 15 МБ
jsonb, то есть не проблема.

Отдельно, плоскими таблицами, хранятся три ряда, по которым строится дашборд и
работает инкрементальность: дневные итоги YAZIO, дневная активность и замеры
тела. Это единственная намеренная денормализация.

## 4. Модель данных

```
account ─┬─< day_snapshot        (сырьё по дню: дневник, активность, вода, цели, самочувствие)
         ├─< account_snapshot    (сырьё уровня аккаунта: профиль, настройки, серия, голодания…)
         ├─< product_cache       (карточки продуктов)
         ├─< recipe_cache        (карточки рецептов)
         ├─< daily_nutrients     (итоги YAZIO по дню — он же детектор изменений)
         ├─< daily_exercise      (шаги, длительность, активные калории по дню)
         ├─< body_value          (вес и прочие замеры)
         ├─< sync_run ──< sync_warning
         └─< export_file
```

| таблица | ключ | назначение |
|---|---|---|
| `account` | email уникален | email, метка, шифрованные пароль и токены, дата регистрации, профиль, флаг автосинка, итог последнего синка |
| `day_snapshot` | (account, date) | шесть jsonb-полей — по одному на дневной эндпоинт — и `fetched_at` |
| `account_snapshot` | (account, kind) | `user`, `settings`, `dietary_preferences`, `subscription`, `streak`, `fasting` |
| `product_cache` | (account, product_id) | карточка продукта целиком; кэш на аккаунт, потому что приватные продукты чужому аккаунту не принадлежат |
| `recipe_cache` | (account, recipe_id) | то же для рецептов, плюс признак «рецепт пользователя» |
| `daily_nutrients` | (account, date) | energy, carb, protein, fat, energy_goal — как их считает сам YAZIO |
| `daily_exercise` | (account, date) | steps, duration, energy |
| `body_value` | (account, kind, logged_at) | weight, body_fat, muscle_ratio, waist, hip, chest |
| `sync_run` | id | режим, период, датасеты, статус, фаза, счётчики, запрос отмены, ошибка |
| `sync_warning` | run | фаза, эндпоинт, ключ, вид, HTTP-статус, сообщение |
| `export_file` | id | параметры сборки, путь к файлу, размер, статистика таблиц |

Даты хранятся строками `YYYY-MM-DD`, отметки времени YAZIO — строками
`YYYY-MM-DD HH:MM:SS`, как их отдаёт API. Причина та же, что в `family-calendar`
(D-006 тамошнего журнала): драйвер `pg` превращает `date`/`time` в объекты
локальной зоны процесса, и это классический источник сдвига на сутки. Служебные
поля самого сервиса (`created_at`, `fetched_at`) — обычные `timestamptz`.

## 5. Синхронизация

### 5.1 Инкрементальность

Дешёвый эндпоинт `consumed-items/nutrients-daily?start&end` возвращает **одним
запросом** дневные итоги за весь период. Он и служит детектором изменений.

```
1.  GET /user                       → дата регистрации, профиль
2.  from = запрошенное ∨ дата регистрации;  to = запрошенное ∨ сегодня
3.  GET nutrients-daily(from, to)   → один запрос на весь период
4.  день попадает в план, если:
      • его нет в day_snapshot;
      • итоги YAZIO разошлись с сохранёнными в daily_nutrients;
      • он входит в окно перепроверки (последние RESYNC_DAYS = 3 дня);
      • запрошена принудительная пересборка.
5.  по каждому дню плана, с лимитом параллельности:
      consumed-items, exercises, water, goals, goals/unmodified, feeling
6.  новые product_id и recipe_id из свежих дней → карточки, которых нет в кэше
7.  диапазонные и аккаунтные, по одному запросу каждый:
      exercises/summary-daily, bodyvalues×6, streak, fasting,
      settings, dietary-preferences, subscription
8.  плоские ряды пересчитываются, run закрывается
```

Первый синк четырёхлетнего аккаунта — порядка 1400 дней × 6 запросов плюс
карточки продуктов. Каждый следующий — единицы запросов: один на детектор,
несколько на изменившиеся дни и диапазонные эндпоинты.

По умолчанию в план идут только дни, о которых YAZIO сообщил данные. Флаг «все
дни» заставляет пройти каждую дату периода — дороже, но ловит день, где есть
цель или самочувствие, но нет еды.

### 5.2 Устойчивость

- **Ошибка одного запроса не роняет синк.** Она становится строкой в
  `sync_warning` — то, что не выгрузилось, видно, а не потеряно молча. Роняют
  синк только две вещи: не прошла авторизация и не ответил детектор изменений.
- **Ретраи** на 429 и 5xx: три попытки, задержка 0.5 → 1 → 2 с плюс разброс.
- **401** — один повтор после обновления токена; если refresh не сработал,
  повторный вход по сохранённому паролю; после этого — провал.
- **Параллельность** ограничена семафором, по умолчанию 6 запросов.
- **Докачка после обрыва** не требует состояния: снимок дня пишется атомарно, а
  план строится заново из разницы «что в БД» и «что говорит YAZIO». Повторный
  запуск после падения продолжает с того же места по построению.
- **Отмена** — флаг в `sync_run`, проверяется между днями.

### 5.3 Прогресс

`sync_run` обновляется по мере работы; UI опрашивает раз в секунду. Вебсокетов
нет: один пользователь, один сервис, поллинг проще и не ломается на разрывах.

## 6. Экспорт

### 6.1 Конвейер

```
сырьё из БД → чистые функции → Table[] → рендерер → файл(ы) → zip при нужде
```

`Table` — это имя, список колонок и строки скалярных ячеек. Ничего вложенного:
именно это позволяет TOON кодировать таблицу компактной табличной формой, а CSV
— вообще существовать.

Ячейка — `null | boolean | number | string`. Округление до двух знаков, а если
значение при этом схлопнулось бы в ноль (селен считают в микрограммах) —
четыре значащих цифры. Целые печатаются без `.0`.

**Отсутствие значения и ноль — разные вещи.** YAZIO не присылает нутриент, о
котором ничего не знает, вместо того чтобы прислать ноль. Пустая ячейка значит
«не отслеживается», ноль значит «отслеживается и равен нулю». В CSV оба выходят
пустым полем, в JSON и TOON различаются.

Колонки нутриентов не фиксированы: в таблицу попадают только те из 54, что
реально встретились в данных. Иначе файл на 90 % состоит из пустоты.

### 6.2 Таблицы

| таблица | строка | примечание |
|---|---|---|
| `meta` | выгрузка | версии, период, счётчики |
| `tables` | таблица | индекс: имя, число строк, колонки |
| `nutrition_log` | запись дневника | нутриенты уже умножены на съеденное количество |
| `daily_summary` | день периода | итоги YAZIO плюс досчитанные микронутриенты |
| `meal_summary` | день × приём пищи | полный разбор по нутриентам |
| `daily_goals` | день × вариант | `effective` и `unmodified` |
| `daily_activity` | день | шаги, дистанция, длительность, активные калории |
| `exercises` | тренировка | залогированные занятия |
| `weight` | взвешивание | |
| `body_values` | замер | жир, мышцы, талия, бёдра, грудь |
| `feelings` | день | заметка и теги настроения |
| `streak` | день | какие приёмы пищи записаны |
| `products` | продукт | нутриенты **на одну базовую единицу** |
| `product_servings` | продукт × порция | «ломтик = 30 г» |
| `recipes` | рецепт | нутриенты **на порцию** |
| `recipe_ingredients` | рецепт × ингредиент | |
| `recipe_instructions` | рецепт × шаг | |
| `profile`, `settings`, `subscriptions` | | уровень аккаунта |
| `fasting_history`, `fasting_periods`, `fasting_patches` | | голодания |
| `warnings` | проблема | пусто на чистом прогоне |

### 6.3 Единицы

YAZIO отдаёт каждый нутриент **в граммах на одну базовую единицу** (грамм или
миллилитр) — не на 100 грамм. Оливковое масло читается как `8.22` ккал. При
переносе в `nutrition_log` умножение на количество уже сделано; в `products`
значения остаются как в API, и это единственное место, где нужна осторожность.

Значения переводятся в единицу, в которой нутриент принято приводить, и колонка
называется соответственно: `energy_kcal`, `carbs_g`, `sodium_mg`, `folate_ug`.

Энергия приходит в килокалориях независимо от того, что выбрано в настройках
профиля (проверено на аккаунте с `unit_energy = kj`).

### 6.4 Сверка

Каждая сборка сравнивает собственную арифметику с дневными итогами YAZIO.
Расхождение больше 0.5 % — строка в `warnings`. Это самая дешёвая проверка того,
что весь экспорт верен: ошибка в масштабировании продукта, неверно прочитанный
рецепт или молча провалившийся запрос ломают сумму того дня, где случились.

Единичные расхождения нормальны: YAZIO хранит итоги такими, какими они были в
момент записи, а сервис пересчитывает по нынешней карточке продукта. Стена
расхождений означает, что сломалось что-то ещё.

### 6.5 Форматы

| формат | раскладка | зачем |
|---|---|---|
| **Markdown** | один файл `digest.md` | готовый отчёт для ИИ |
| **JSON** | один файл `export.json` | полный машинный дамп |
| **TOON** | один файл `export.toon` | то же содержимое, имена колонок один раз в заголовке |
| **CSV** | файл на таблицу | Excel и инструменты анализа |

Если файлов больше одного — на выходе zip.

TOON пишется по спецификации `toon-format/spec`: заголовок
`name[N]{col1,col2}:`, строки с отступом в два пробела, кавычки вокруг значения,
если оно пустое, похоже на число, содержит разделитель, двоеточие, кавычку или
краевые пробелы.

### 6.6 Markdown-дайджест

Ради него всё и затевалось: один файл, который вставляется в чат с ИИ.

1. Как читать этот файл: единицы, что пустое значение ≠ ноль, границы периода.
2. Профиль и цели: пол, возраст, рост, цель, темп, PAL, раскладка БЖУ.
3. Полнота данных: сколько дней с записями из скольких, какие пропущены.
4. Сводка периода: калории и БЖУ — среднее, медиана, разброс, отклонение от
   цели, доля дней в пределах ±10 %.
5. Вес: старт, финиш, дельта, недельные средние, линейный тренд.
6. Активность: шаги и активные калории.
7. Ряд по дням: дата, калории, цель, БЖУ, клетчатка, шаги, вес. При периоде
   длиннее 400 дней ряд сворачивается в недельный — иначе файл перестаёт
   помещаться в контекст модели.
8. Приёмы пищи: средние по завтраку, обеду, ужину, перекусам.
9. Топ продуктов: по вкладу в калории и по частоте.
10. Микронутриенты: среднее за сутки и в какой доле дней нутриент вообще
    фиксировался — без этой доли среднее вводит в заблуждение.
11. Качество данных: расхождения сверки, пропуски, неизвестные ключи.

Сервис не сравнивает потребление с нормами и не даёт рекомендаций — он даёт
факты и профиль, а выводы делает та модель, которой отдали файл (D-009).

## 7. Web-интерфейс

Nuxt 4, SPA, два языка, свой CSS, тёмная и светлая темы. Собранная статика
раздаётся самим NestJS — один процесс, один порт, нет CORS.

| экран | что делает |
|---|---|
| `/login` | вход в сервис по паролю |
| `/` | список аккаунтов: последний синк, дней в базе, период; здесь же собирается демо-аккаунт (D-068) |
| `/accounts/new` | добавить аккаунт: email, пароль, метка; вход проверяется сразу |
| `/accounts/[id]` | обзор: имя аккаунта и свежесть данных; сводка за выбранный период — расход, съедено, баланс, вердикт по дефициту, полоски «съедено против расхода» и таблица прогресса, у каждого числа сказано, по скольким дням оно посчитано (D-082) |
| `/accounts/[id]/journal` | день целиком: приход и расход рядом, раскрытие до состава приёма пищи, разбор расхода и оценка дня; отбор дней с обеими половинами и не меньше чем тремя приёмами пищи (D-054, D-078); сортировка по оценке, белку, калориям и калориям тренировок (D-072) |
| `/accounts/[id]/planner` | режим: нормы двумя колонками, конструктор меню и тренировок, шаблоны; над списком дней — что означают «цель», «в меню» и «баланс», её же числами (D-079) |
| `/accounts/[id]/plans` | сохранённые планы: метки, поиск по названию, страницы, выгрузка в PDF |
| `/accounts/[id]/plans/[planId]` | план целиком, только чтение: дни, меню, тренировки (D-049); пояснение к числам — из норм, сохранённых вместе с планом (D-079) |
| `/accounts/[id]/guide` | как это работает: формулы, схемы и все настройки человеческим языком |
| `/accounts/[id]/data` | просмотр базы: дневник, дни, продукты, замеры, Apple Health — с фильтрами и постранично |
| `/accounts/[id]/sync` | синхронизация и её расписание, выгрузка из Google Drive, загрузка Apple Health, доступ к аккаунту; у демо вместо этого пересборка истории |
| `/accounts/[id]/export` | конструктор выгрузки: период, датасеты, форматы, гранулярность, обезличивание → сборка → скачивание |
| `/fields` | справочник полей: что в каком поле хранится, для просмотра и для выгружаемых файлов |
| `/exports` | все собранные файлы, скачивание и удаление |

Навигация одна на все разделы — верхняя строка в макете (D-037, D-067): четыре
главных раздела на виду, остальные под «Ещё», служебное под шестерёнкой.

**Демо-аккаунт.** Кнопка на `/` собирает аккаунт с выдуманной историей за
полгода — дневник, шаги, сон, тренировки, вес и один сохранённый план (D-068).
Данные ложатся в те же таблицы, что и настоящие, и считаются тем же кодом:
отдельной ветки «если демо» в расчётах нет. Синхронизации у него нет, и раздел
«Синхронизация» показывает ему только пересборку и удаление.

Графики — свои SVG-спарклайны на полсотни строк. Тянуть библиотеку графиков
ради двух линий незачем.

### 7.1. Два языка

Словари обоих языков лежат в `@fatoff/contracts` — тем же текстом подписывается
PDF. Сервер фраз не сочиняет: в DTO едет `Message = { code, params }`, а
предложение собирает фронт (D-044). Справочники — настройки, поля, нутриенты —
несут обе версии рядом, `Text = { ru, en }`.

Выбранный язык лежит в `localStorage` под `fatoff:locale` и ставится в атрибут
`lang` документа. Забытый перевод ловится тестами и прогоном в браузере, а не
глазами (D-045).

### 7.2. План одним файлом PDF

`pdfkit`, макет описан кодом, шрифты встроены в документ (D-046). У каждого
числа на листе стоит подпись, а на первой странице напечатано «как читать»
(D-050): навести мышь на бумагу нельзя. Дата сборки передаётся снаружи, поэтому
два прогона на тех же данных дают одинаковые байты — как и у выгрузки (D-010).

## 8. Безопасность

- Вход в сервис — один пароль (`APP_PASSWORD`), сессия в подписанной httpOnly
  cookie, попытки входа ограничены `@nestjs/throttler`.
- Пароль YAZIO и оба токена лежат в БД под **AES-256-GCM**; ключ (`SECRETS_KEY`)
  живёт в `.env`, то есть вне базы. Дамп базы без ключа бесполезен.
- Пароля может не быть вовсе: аккаунт с входом через Apple ID добавляется
  готовым токеном и живёт на нём, пока YAZIO этот токен не отзовёт (D-017).
- Пароли и токены не попадают в логи: сериализатор Pino вырезает поля по имени.
- Сервис слушает локально; наружу его выставлять не предполагается.
- Экспорт умеет обезличивание: профильные поля (email, uuid, имя, дата
  рождения, город) заменяются пустыми — стоит включать перед отправкой файла
  куда-то ещё.

## 9. Тесты

Vitest. Основная масса — на чистых функциях, потому что архитектура специально
собрана так, чтобы вся арифметика была чистой.

### 9.1 Модульные, без базы и сети

| файл | что доказывает |
|---|---|
| `nutrients.spec` | маппинг 54 ключей, множители единиц, суммирование разреженных наборов, отсутствующий ключ не превращается в ноль |
| `cell.spec` | округление, схлопывание в целое, четыре значащих цифры для микрограммов, `null` против пустой строки |
| `tables/nutrition-log.spec` | масштабирование продукта на количество, рецепт на число порций, быстрая запись без масштабирования, неизвестный продукт не роняет строку |
| `tables/daily-summary.spec` | строка на каждый день периода, макросы берутся у YAZIO, микронутриенты досчитываются, невыгруженный день — пусто, а не нули |
| `tables/meal-summary.spec` | группировка по дню и приёму пищи, счётчик записей |
| `tables/*.spec` | цели, активность, вес, замеры, самочувствие, серия, продукты, рецепты, профиль, настройки, голодания |

| `renderers/markdown.spec` | структура разделов, недельная свёртка на длинном периоде, доля дней с нутриентом |

### 9.2 Интеграционные, с базой и фейковым YAZIO

Фейк — локальный http-сервер на фикстурах: умеет отдавать 401, 429, 500 и
обрывать соединение, чтобы проверялись не только счастливые пути.

| файл | что доказывает |
|---|---|
| `sync.spec` | полный синк наполняет базу; повторный запуск не делает лишних запросов; изменившийся день перекачивается; сбой на одном дне даёт предупреждение, а не падение; синк после обрыва доходит до конца |
| `exports.spec` | сборка из базы даёт файлы всех форматов; два прогона на тех же данных дают побайтово одинаковый результат; zip собирается при нескольких файлах |
| `accounts.spec` | добавление с проверкой входа, шифрование в БД, удаление уносит все данные аккаунта |
| `api.spec` | маршруты за авторизацией отвечают 401 без сессии; ключевые сценарии проходят через HTTP |

### 9.3 Проверка живого API

`pnpm --filter @fatoff/api run check:yazio` — отдельная команда, не в тестах:
проходит по всем эндпоинтам живого аккаунта и печатает, какие ещё отвечают.
Нужна потому, что API недокументировано и может измениться в любой момент.

### 9.4 Фикстуры

Обезличенные ответы v9 с живого аккаунта плюс синтетический десятидневный
аккаунт: сплит-смены приёмов пищи, быстрые записи, рецепты, пропущенные дни,
день с расхождением сумм, продукт с семью нутриентами против продукта с сорока.

## 11. Конфигурация

```
PORT=4090                     LOG_LEVEL=info
APP_PASSWORD=                 пароль входа в сервис
SESSION_SECRET=               подпись сессионной cookie
SECRETS_KEY=                  32 байта hex — ключ шифрования учётных данных YAZIO
DB_HOST/PORT/NAME/USER/PASSWORD, DB_AUTO_MIGRATE=true
YAZIO_API_BASE=https://yzapi.yazio.com
YAZIO_API_VERSION=v9          v22 проверяет версию клиента и может закрыться
YAZIO_CONCURRENCY=6           одновременных запросов
YAZIO_RESYNC_DAYS=3           хвост, который перекачивается всегда
EXPORT_DIR=../../storage/exports
EXPORT_RETENTION_DAYS=30      0 — не удалять
SCHEDULES_ENABLED=true        фоновые расписания в этом окружении
```

Три поля обязательны и не имеют значений по умолчанию: `APP_PASSWORD`,
`SESSION_SECRET`, `SECRETS_KEY`. Сервис не стартует, пока они не заданы.
