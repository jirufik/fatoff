# Архитектура: день целиком и генератор режима

Две задачи, разные по природе, но на одних данных.

1. **День целиком** — чтение. Свести YAZIO и Apple Health в одну раскрывающуюся
   строку: приход → приёмы пищи → продукты; расход → шаги и тренировки; баланс
   цветом и числом; оценка дня.
2. **Генератор режима** — счёт. Из её собственных продуктов и её же истории
   тренировок собрать меню и расписание на день, неделю, месяц или произвольный
   период, с шаблонами.

Числа и рекомендации, на которых всё стоит, разобраны в
[`ANALYSIS-NUTRITION.md`](./ANALYSIS-NUTRITION.md). Здесь — как это устроено в коде.

---

## 1. Общие решения

**Где берутся данные.** Ничего нового не выкачивается. Всё считается из уже
лежащего в базе: `day_snapshot` (сырые ответы YAZIO), `product_cache`,
`daily_nutrients`, `body_value`, `health_daily`, `health_workout`, `health_sleep`.

**Где живёт счёт.** Новый модуль `modules/planner`. Внутри — чистые функции без
базы и сети: нормы, оценка дня, подбор меню, расстановка тренировок. Сервисы
только достают строки и отдают их этим функциям. Это то же разделение, что уже
работает в `sync-plan.ts` и `exports/build.ts`, и по той же причине: чистое
покрывается тестами без поднятой базы.

**Где живёт чтение дня.** Новый модуль `modules/journal`. Отдельно от `browse`
намеренно: `browse` показывает таблицы как они лежат, `journal` собирает из
нескольких таблиц одну картину дня. Смешивать — получить сервис, который делает
два разных дела.

**Детерминированность.** Генератор при тех же входных данных и том же зерне даёт
тот же план. Зерно хранится вместе с планом, поэтому сохранённый план
воспроизводится, а «сгенерировать ещё вариант» — это просто другое зерно.

**Настройки — данные, а не код.** Всё, что определяет поведение генератора,
описано записями в `PLANNER_SETTINGS`: значение по умолчанию, границы,
рекомендованный участок, источник рекомендации и текст описания. По этому списку
интерфейс строит форму, по нему же сервер приводит пришедшие значения к
границам. Записанные порознь, они разошлись бы молча: подпись сказала бы одно,
проверка пропустила другое, алгоритм посчитал третье.

## 2. День целиком

### 2.1 Два запроса вместо одного

Раскрытие дня грузит подробности отдельно. Причина простая: на 3137 днях
подгрузить сразу все приёмы пищи и все тренировки — это десятки тысяч строк
ради двадцати видимых.

```
GET /api/accounts/:id/journal/days?from&to&page&pageSize&sort&dir&onlyWithFood
    → PageDto<JournalDayDto>   строка дня: итоги, счётчики, баланс, оценка

GET /api/accounts/:id/journal/days/:date
    → JournalDayDetailDto      приёмы пищи с составом, тренировки, разбор оценки
```

Список считается одним запросом на всю страницу — не N+1 на каждый день.
Подробности — по клику, с кэшем на стороне страницы: повторное раскрытие того же
дня в базу не ходит.

### 2.2 Что в строке дня

```ts
interface JournalDayDto {
  date: IsoDate;
  // приход
  energyInKcal: number | null;
  carbsG / proteinG / fatG / fiberG: number | null;
  meals: number;          // сколько приёмов пищи было
  entries: number;        // сколько записей всего
  // расход
  activeKcal / basalKcal / energyOutKcal: number | null;
  steps: number | null;
  workouts: number;       // сколько тренировок
  workoutKcal: number | null;
  exerciseMin: number | null;
  // сведение
  balanceKcal: number | null;   // приход − расход
  balance: 'deficit' | 'even' | 'surplus' | null;
  // прочее
  asleepMin: number | null;
  weightKg: number | null;
  score: number | null;         // 0–100
}
```

`balance` — отдельное поле, а не вывод из знака числа на клиенте. «Ноль» это не
ровно ноль, а коридор ±100 ккал: складывать оценку часов с оценкой дневника
точнее нельзя, и делать вид, что 12 ккал — это профицит, нечестно.

Цвет берётся из `balance`, число — из `balanceKcal`. Оба видны одновременно,
как и просили: цвет читается краем глаза, число — когда нужно точно.

### 2.3 Что в подробностях

```ts
interface JournalDayDetailDto {
  date: IsoDate;
  meals: JournalMealDto[];      // завтрак/обед/ужин/перекус, с КБЖУ каждого
  workouts: JournalWorkoutDto[]; // тип, время, длительность, ккал, источник
  burn: {                        // из чего сложился расход
    basalKcal, activeKcal, workoutKcal, steps, distanceKm, exerciseMin
  };
  score: ScoreBreakdown;         // разбор оценки по составляющим
}

interface JournalMealDto {
  meal: 'breakfast' | 'lunch' | 'dinner' | 'snack';
  energyKcal, carbsG, proteinG, fatG, fiberG: number | null;
  items: JournalItemDto[];       // название, граммовка, порция, КБЖУ
}
```

Три уровня раскрытия — день, приём пищи, состав — это одна структура; второй
клик ничего не догружает, он разворачивает уже полученное.

Тренировки — из `health_workout`, а не из YAZIO. В YAZIO упражнения тоже есть,
но часы знают о них больше и точнее. Расхождение между `activeKcal` из Health и
суммой тренировок ожидаемо: активная энергия включает всё движение за день, а не
только записанные тренировки; в разборе они показаны отдельными строками, а не
одной суммой, чтобы это не выглядело ошибкой.

### 2.4 Оценка дня

«Насколько продуктивный день» — число, за которым видно, из чего оно сложилось.
Шесть составляющих, каждая со своим источником из
[`ANALYSIS-NUTRITION.md`](./ANALYSIS-NUTRITION.md):

| составляющая | вес | зачёт |
|---|---|---|
| энергетический баланс | 20 | дефицит в коридоре 200–500 ккал |
| белок | 20 | не ниже расчётной нормы |
| клетчатка | 10 | не ниже 14 г на 1000 ккал |
| шаги | 15 | не ниже цели (10 000) |
| движение | 15 | не ниже 21 минуты (150 в неделю по ВОЗ) |
| сон | 20 | 7–9 часов |

Каждая даёт долю от веса по линейной шкале, а не «да/нет»: 9500 шагов из 10 000
это не ноль. Составляющая, по которой данных нет, из знаменателя выпадает — день
без записи о еде не должен получать двойку за то, что о нём просто неизвестно;
`covered` показывает, сколько составляющих участвовало.

Отдельно от оценки — **предупреждение об энергодоступности**: если
(съедено − энергия тренировок) / БЖМ ниже 30 ккал/кг, день помечается, даже если
формально «дефицит по плану». Это не штраф к баллам, а флаг: смысл у него другой,
и смешивать его с оценкой значит его спрятать.

```ts
interface ScoreBreakdown {
  total: number;                 // 0–100
  covered: number;               // сколько составляющих посчитано
  parts: Array<{
    key: string; title: string;
    value: number | null; target: number; weight: number;
    earned: number; note: string;   // «9 500 из 10 000 шагов»
  }>;
  lowEnergyAvailability: boolean;
  energyAvailability: number | null;
}
```

## 3. Нормы

Чистый модуль `planner/targets.ts`. На входе — профиль, состав тела, медианы
расхода из Health и цели из YAZIO. На выходе — обе колонки цифр.

```ts
computeTargets(input: TargetsInput): TargetsDto
```

Порядок счёта повторяет § 3 анализа:

1. базальный обмен — из Health (медиана), формула Миффлина–Сан-Жеора рядом как проверка;
2. полный расход = активный + базальный;
3. дефицит — из выбранного темпа снижения (% массы в неделю → ккал/день);
4. целевые калории = расход − дефицит;
5. белок = г/кг × масса, жиры = г/кг × масса, углеводы — остаток;
6. клетчатка = 14 г на 1000 ккал; порог белка за приём = 0.4 г/кг;
7. энергодоступность при этих целях — с проверкой порога 30.

`TargetsDto` содержит **три** набора чисел: `computed` (расчёт), `yazio` (что
стоит в приложении) и `diff`. Показываются все — по прямой просьбе. Каждое
расчётное число несёт `basis` — короткую строку, откуда оно взялось
(«1.8 г/кг × 58 кг», «ISSN 1.4–2.0, верх диапазона при дефиците»), чтобы цифра в
интерфейсе не была цифрой ниоткуда.

Темп снижения — параметр, не константа: ползунок 0.3–1.0 % массы в неделю с
пометкой рекомендованного участка.

## 4. Генератор

### 4.1 Пул продуктов

`planner/food-pool.ts` собирает из дневника список того, что она **правда ест**.

Для каждого продукта: сколько раз встречался, в каких приёмах пищи, типичная
граммовка (медиана, а не среднее — одна запись в 400 г не должна двигать
типичную порцию), КБЖУ на единицу, клетчатка, когда ел в последний раз.

Отбор: встречался не реже трёх раз и хотя бы раз за последний год. Всё остальное
— шум: случайно отсканированный штрих-код в кафе два года назад не должен
попасть в план на следующую неделю.

Продукт привязан к приёмам пищи, в которых она его ела. Овсянка не поедет в ужин
только потому, что по КБЖУ подошла.

Тот же файл строит **каталог комплектов** — приёмов пищи из дневника, взятых
целиком (D-073). Комплект попадает в каталог, только если каждое его блюдо
прошло отбор пула; одинаковые составы схлопываются, граммовка берётся медианой
по повторам. Комплект легче 50 ккал — обрывок записи, а не еда.

Откуда что берётся, задаёт `MEAL_SOURCES`: завтрак — только из завтраков, обед и
ужин делят один каталог, перекус остаётся при себе. Правило одно и на комплекты,
и на отдельные блюда.

### 4.2 Подбор меню

Приём пищи берётся из дневника целиком, а не собирается из блюд (D-073).

```
перекус — первым, по своему правилу:
  самый лёгкий из её перекусов, не повторявшийся в окне;
  цели по калориям у него нет, остаток дня достаётся основным

для каждого основного приёма, по очереди:
  1. цель = остаток дня × доля среди ещё не собранных приёмов,
     но белок не ниже 0.4 г/кг
  2. перебор комплектов нужного приёма; каждый масштабируется
     одним коэффициентом (0.5–1.6), состав не трогается
  3. выигрывает ближайший по оценке; остаток дня уменьшается
     на то, что он правда занял
```

Оценка набора — взвешенная сумма отклонений: калории (вес 3), белок (3),
углеводы (1), жиры (1), клетчатка (1, только в минус при недоборе), плюс штраф
за повтор. Число позиций комплекту не в счёт: его состав выбирали не мы.

Граммовки округляются к разумному шагу — 5 г, либо к кратному порции, если у
продукта есть порция («штука», «ложка»). План с «73.4 г творога» никто выполнять
не станет.

**Поблюдная сборка осталась** и работает в двух случаях: каталог приёма пуст или
человек закрепил в приёме блюдо. Тогда идёт прежний лучевой поиск — на каждом
шаге добавляется продукт, держатся K лучших частичных наборов, потом локальное
улучшение заменами и граммовками.

Ограничения проверяются на выходе, а не только внутри поиска: калории в ±5 % от
цели, белок не ниже порога, клетчатка за день не ниже нормы. Если сойтись не
удалось — генератор **говорит, чего не хватило**, а не выдаёт лучший из плохих
молча. С комплектами это случается чаще, чем с поблюдной сборкой, и это цена
решения, а не его поломка: выбирать приходится из готового, а не собирать под
число.

### 4.3 Тренировки

`planner/training-plan.ts`, четыре режима — все выбираются в интерфейсе:

| режим | что делает |
|---|---|
| `current` | сохраняет нынешний объём, расставляет по правилам восстановления |
| `who` | 150–300 мин умеренного + 2 силовых по ВОЗ |
| `manual` | тренировки задаёт человек, генератор подгоняет под них питание |
| `goal` | объём выводится из целевого дефицита и восстановления |

Правила расстановки общие для всех режимов: силовые не два дня подряд, длинное
кардио не в один день с силовыми, минимум один день полного отдыха, длинное — на
выходные (по её же истории видно, когда она реально тренируется дольше).

Типы и длительности берутся из её тренировок: ходьба, бег, силовая, эллипс,
велосипед, функциональная, ВИИТ, плавание — с её же средними длительностью и
затратами, а не с табличными.

### 4.4 День и период

```
generate(period, settings) =
  расставить тренировки на период
  → для каждого дня: цель — одна и та же на весь план
  → подобрать меню под цель дня: перекус первым, затем основные
  → проверить день (баланс, белок, клетчатка, энергодоступность)
  → окно разнообразия скользит по дням: не повторяются ни блюдо,
    ни комплект целиком
```

Целевая калорийность одинакова во все дни плана (D-074): так просил заказчик, и
так план проще выполнять. Прибавка энергии тренировки осталась настройкой и
выключена по умолчанию. Включать её есть за что: без прибавки в дни с часовой
пробежкой дефицит удваивается, а именно это и роняет энергодоступность (§ 2.3
анализа). Поэтому проверка энергодоступности каждого дня никуда не делась — день,
упавший ниже 30 ккал/кг, помечается.

Период — любой: день, неделя, месяц, произвольные даты. Разница только в длине
окна разнообразия.

### 4.5 Правка руками

Сгенерированный план — не приговор. В готовом дне блюдо можно заменить на другое
из её же пула, изменить граммовку или **закрепить**: закреплённое переживает
следующую сборку и встаёт в тот же приём пищи, а генератор добирает остальное
вокруг него. Так решается и «хочу этот завтрак всю неделю», и «сегодня вот это,
а дальше как получится».

Пересчёт после правки идёт на сервере (`POST /planner/recost`) той же сборкой
дня, что и генерация. Считать в браузере было бы быстрее, но тогда арифметики
стало бы две, и разошлись бы они молча — разными числами на одной странице.

### 4.6 Из чего собирать

Пул сужается двумя способами, и оба нужны:

- **периодом дневника** — «бери то, что она ела с этой даты по эту». Лето и зима
  у неё едятся по-разному, и план на август из январских продуктов бесполезен;
- **отмеченным набором** — человек сам выбирает блюда из списка, и генератор
  собирает только из них.

Оба приходят в запросе полем `pool`, а не настройкой: это не тонкая подстройка
алгоритма, а ответ на вопрос «из чего», который меняется от раза к разу.

### 4.7 Хранение

Две таблицы:

```
meal_plan      план на период: даты, настройки, зерно, дни (jsonb), нормы (jsonb)
plan_template  шаблон: имя, описание, настройки; свои и встроенные
```

План хранится собранным, а не пересчитывается при каждом открытии: пул продуктов
меняется по мере синхронизации, и сохранённый на прошлой неделе план должен
остаться тем, что человек видел, когда его сохранял.

Встроенные шаблоны живут в коде (`planner/templates.ts`), а не в базе: это часть
поставки, их не редактируют, и миграция для них не нужна.

### 4.6 Эндпоинты

```
GET  /api/accounts/:id/planner/settings           справочник настроек: описания и границы
GET  /api/accounts/:id/planner/targets?rate=      нормы: расчёт и цели YAZIO рядом
GET  /api/accounts/:id/planner/pool?from&to      пул продуктов
POST /api/accounts/:id/planner/recost            пересчёт дня после ручной правки
POST /api/accounts/:id/planner/generate           сгенерировать (не сохраняя)
GET  /api/accounts/:id/planner/plans              сохранённые планы
POST /api/accounts/:id/planner/plans              сохранить план
GET  /api/accounts/:id/planner/plans/:planId
DELETE /api/accounts/:id/planner/plans/:planId
GET  /api/accounts/:id/planner/templates          встроенные и свои
POST /api/accounts/:id/planner/templates          сохранить шаблон
DELETE /api/accounts/:id/planner/templates/:tplId
```

`generate` ничего не сохраняет — можно жать «ещё вариант» сколько угодно.
Сохранение отдельным действием, с уже полученным планом в теле запроса.

## 5. Интерфейс

Четыре страницы в общей навигации аккаунта: «Дни», «Режим», «Планы» и
«Как это работает».

**`/accounts/:id/journal` — «День целиком».** Список дней, каждый — строка с
итогами; цвет фона у числа баланса: дефицит, ноль, профицит. Клик раскрывает
приёмы пищи с КБЖУ каждого и блок расхода с тренировками. Клик по приёму пищи
раскрывает состав. Раскрыт всегда один день и один приём, поэтому раскрытие
убирает со страницы соседний блок — нажатая строка при этом удерживается на
месте вручную, а не надеждой на браузер (D-075). Оценка — кружком с числом, при наведении — разбор по
составляющим. Фильтр по периоду и «только дни с едой», пагинация — как в
существующем просмотре.

**`/accounts/:id/guide` — «Как это работает».** Объяснение генератора для
человека, а не для программиста: коротко в начале, дальше формулы расчёта норм,
схема порядка работы, шкала энергодоступности, схема направленного поиска,
правила расстановки тренировок, разбор всех настроек и честный список того, чего
генератор не делает. Таблица настроек строится из того же справочника, что и
форма конструктора (D-027), а числа в примерах подставляются из её расчёта:
объяснение не может разойтись ни с кодом, ни с данными.

**`/accounts/:id/planner` — «Режим».** Сверху нормы двумя колонками с разницей и
подписью, откуда взялось каждое расчётное число. Ниже конструктор: период, режим
тренировок, приёмы пищи.

Настройки — в два уровня. Сразу видно пять: темп снижения веса, прибавка энергии
тренировки, число позиций в приёме, окно разнообразия и повторы в нём. Остальные
двадцать пять — за одним раскрытием, разложенные по шести группам («Целевые
числа», «Распределение по приёмам пищи», «Подбор блюд», «Разнообразие», «Из чего
выбирать», «Во что целиться»), и у каждой описание, границы, рекомендованный
участок и источник. Простое видно сразу, сложное доступно, но не навязано.

Кнопки «Сгенерировать», «Ещё вариант», «Пересобрать с тем же зерном»,
«Сохранить». Результат — дни с меню и тренировками, с итогами и
предупреждениями. Рядом — шаблоны: встроенные и сохранённые.

**`/accounts/:id/plans` — «Планы».** Сохранённое живёт отдельно от генератора
(D-047): планов быстро становится много. Метки задаёт человек и приводятся к
нижнему регистру без повторов, поиск идёт по названию без учёта регистра,
список постранично. План открывается в конструкторе и выгружается одним файлом
PDF на выбранном языке (D-046).

Навигация одна и живёт в раскладке (D-037, D-067): одна полоса, в ней аккаунт,
четыре главных раздела, «Ещё» с остальными и шестерёнка со служебным. Отдельных
рядов кнопок, хлебных крошек и кнопок «назад» на страницах нет.

Все страницы — на существующей системе стилей проекта, без новых зависимостей.

**Как читаются числа.** КБЖУ различаются тремя признаками сразу — буквой, цветом
и формой метки, — потому что одной буквы мало, а одного цвета недостаточно при
дальтонизме. Оценка дня объяснена рядом с ней: что означает число и что означает
цвет кольца; полоски составляющих красятся по уровню, а не одинаково. У каждой
настройки и у расчёта норм стоит ссылка на источник — не на слово, а по ссылке.

**Узкий экран.** Обе страницы проверяются прогоном на 360 пикселях: страница не
должна ехать вбок, и свою боковую прокрутку не должен заводить кусок внутри неё.
Строки дней переносятся, таблицы прокручиваются внутри себя, разделы схлопываются
под текущий — полоса остаётся в одну строку и не выше 46 пикселей (D-067).

## 6. Что проверяется тестами

Чистое ядро — модульными, без базы:

- нормы: формула Миффлина на известных значениях; распределение макросов даёт
  ровно целевые калории; энергодоступность считается и порог срабатывает;
- оценка дня: полный день даёт 100; отсутствующая составляющая выпадает из
  знаменателя, а не обнуляет; линейная шкала на границах;
- пул: медиана порции устойчива к выбросу; редкие и старые продукты отсеиваются;
- каталог комплектов: приём одного дня собирается целиком; блюдо мимо пула
  забирает с собой весь комплект; одинаковые составы схлопываются; крошка
  комплектом не считается;
- отбор по приёмам: в завтрак идут только завтраки, обед и ужин берут еду друг у
  друга, перекус остаётся при своём;
- подбор комплектом: состав берётся целиком, размер — одним коэффициентом и не
  дальше полутора порций, съеденный на неделе комплект уступает место другому;
- перекус: самый лёгкий из её перекусов, назавтра — следующий по лёгкости;
- подбор: калории в ±5 %, белок не ниже порога, клетчатка за день добирается;
  повтор продукта не чаще заданного; **одно зерно — один и тот же план**; когда
  сойтись нельзя, приходит объяснение, а не молчаливый мусор;
- цели дня: все дни плана одинаковы по калорийности, а включённая прибавка снова
  поднимает тренировочный день;
- тренировки: во всех четырёх режимах силовые не подряд, есть день отдыха, объём
  режима `who` попадает в диапазон ВОЗ.

Через базу — интеграционными: день целиком собирается из синтетического аккаунта
с известными числами; подробности дня совпадают с итогами строки; генерация,
сохранение, чтение и удаление плана и шаблона; настройки из браузера приводятся
к границам справочника.

Планы — интеграционными: метки приводятся к порядку и повторы схлопываются;
отбор по нескольким меткам работает как «и», а не «или»; поиск без учёта
регистра; страницы режут список, а «всего» считается после фильтра; чужой план
не читается, не правится и не удаляется. PDF — оттуда же: файл собирается, свой
шрифт встроен, язык меняет содержимое, а два прогона на тех же данных дают
одинаковые байты.

Интерфейс — прогоном в браузере (`apps/web/scripts/check-ui.mjs`): день
раскрывается до состава приёма пищи, нажатая строка при этом не уезжает
(проверяется с намеренно выключенным `overflow-anchor`, иначе Chrome удержал бы
её сам и проверка ничего не стерегла бы), вся сложность настроек прячется за
одним раскрытием, шаблон меняет режим тренировок и объём. Тот же прогон переключает
язык на английский и обходит все разделы в поисках забытого перевода (D-045).
