# Доска задач FatOFF: от замечания до прода

Замечания приходят не в трекер, а в документ на Google Drive. Этот скилл описывает путь от
строчки в чужом документе до влитой в прод задачи, целиком и по шагам.

## Ограничение, из которого выросло всё устройство

**Сервисный аккаунт не может владеть файлами на Drive.** Его квота — ноль:

```
about?fields=storageQuota  →  {"limit":"0"}
files.create (документ)    →  403 storageQuotaExceeded
files.create (папка)       →  200
```

Папки ничего не весят, поэтому их сервис создаёт свободно; файлы списываются с владельца,
поэтому создать их он не может, но **править файлы человека — может**. Отсюда разделение (D-070):

| что | где | кто заводит | кто ведёт |
|---|---|---|---|
| статус задачи | в имени папки `tasks/T-03 · Название · в работе` | сервис | сервис |
| текст задачи, критерии, история | документ внутри папки задачи | **человек** | сервис |
| общая картина по всем задачам | документ доски в `tasks/` | **человек** | сервис |
| замечания заказчика | документ заказчика | заказчик | заказчик |

Заводя новую задачу, сервис создаёт папку сам, а документ в ней — просит создать человека.
Пустого документа достаточно: имя и содержимое сервис проставит.

**У свежесозданной задачи документа может не быть.** `task <T-xx>` в этом случае честно
скажет, что документа нет, — это не поломка, а повод попросить один клик.

Не пытайся создавать файлы сервисным аккаунтом — вернётся 403, и это не чинится настройками.
Если нужен новый документ, попроси человека создать пустой и скажи, где.

## Где что лежит

Идентификаторы личные и в git не едут — они в `.env`, образец в `.env.example`:

- `DRIVE_NOTES_DOC` — документ, куда заказчик пишет замечания;
- `DRIVE_TASKS_FOLDER` — папка `tasks`, статусы в именах подпапок;
- `DRIVE_TASKS_DOC` — документ доски; пока пуст, значит человек его ещё не создал;
- `DRIVE_FATOFF_FOLDER` — корневая папка проекта.

Инструмент: `scripts/task-board.mjs` (поверх `scripts/drive-api.mjs`).

```bash
node scripts/task-board.mjs notes                 # замечания заказчика
node scripts/task-board.mjs list                  # доска: задачи и статусы
node scripts/task-board.mjs add T-08 «Название»   # завести задачу
node scripts/task-board.mjs status T-03 «в работе»
node scripts/task-board.mjs pull                  # прочитать документ доски
node scripts/task-board.mjs push доска.txt        # переписать документ доски
node scripts/task-board.mjs task T-03             # прочитать документ задачи
node scripts/task-board.mjs task T-03 текст.txt   # переписать документ задачи
```

Статусы: `ожидает` → `в работе` → `на проверке` → `готово`. Плюс `отложена` и `вопрос` —
последний означает, что задача стоит из-за неясности и ждёт ответа, а не работы.

## Порядок работы

### 1. Разобрать замечания

Прочитай `notes`. Каждое замечание — это одна задача или несколько: один пункт заказчика
нередко содержит две разные правки (например, «сортировка» и «фильтр по числу приёмов пищи» —
это две задачи, а не одна). Дели по тому, что можно отдельно сделать и отдельно проверить.

**Неясности не угадывай.** Замечание вроде «зафиксировать верхнее меню» может значить липкую
шапку, отказ прятать разделы или «больше не менять». Ставь статус `вопрос` и спрашивай —
угаданная задача хуже незаданного вопроса, потому что её потом переделывать.

### 2. Одна задача — одна ветка

Порядок общий для проекта и нарушать его нельзя (D-069):

```bash
git switch develop
git switch -c feature/<коротко-о-задаче>
node scripts/task-board.mjs status T-03 «в работе»
# … работа …
pnpm test && pnpm build
ACCOUNT=… PASSWORD=… BASE=http://localhost:4291 node apps/web/scripts/check-ui.mjs
pnpm run dev                       # показываем с фича-контура: http://<ip>:4291
node scripts/task-board.mjs status T-03 «на проверке»
```

Дальше **ждём слова человека**. Слить в `develop` без спроса нельзя, и хук это проверяет:

```bash
APPROVED_BY="кто одобрил" git merge --no-ff feature/<ветка>
node scripts/task-board.mjs status T-03 «готово»
```

### 3. Документация обновляется вместе с кодом

Это требование заказчика, а не пожелание: документы должны описывать то, что есть сейчас.
В той же ветке, что и код:

- `docs/DECISIONS.md` — новое решение, если задача его содержит: что выбрано, почему,
  какая цена. Не пересказ кода, а то, чего по коду не видно;
- `docs/ARCHITECTURE.md` или `docs/PLANNER-ARCHITECTURE.md` — если поменялся состав экранов,
  модель данных, конвейер;
- `README.md` — если поменялось то, что видит человек при запуске;
- `CLAUDE.md` — если появилась грабля, на которую наступит следующая сессия;
- прогон в браузере `apps/web/scripts/check-ui.mjs` — если поведение можно проверить машиной.
  Новая проверка должна **падать на старом поведении**: убедись в этом, временно вернув его.

Задача без обновлённой документации не считается готовой.

### 4. Отчитаться

Статус на доске — это минимум. В ответе человеку: что сделано, что проверено, где посмотреть,
и **что осталось неясным**. Если по дороге выяснилось, что замечание понято неверно, — сказать
об этом прямо, а не молча сделать по-своему.

## Что писать в документ доски

Документы ведутся целиком: и `push`, и `task <id> <файл>` переписывают документ. Поэтому
перед правкой — `pull` или `task <id>`, иначе затрётся то, что человек дописал руками.
Черновики держи во временной папке, а не в репозитории: источник правды — Drive, там их
читает заказчик.

Формат — по задаче на раздел:

```
T-03 · Сортировка в «День целиком» · готово
Замечание: пункт 3 документа замечаний.
Что делаем: сортировка списка дней по оценке, белку, калориям, калориям тренировок.
Критерии приёмки: переключатель виден на странице; порядок меняется; выбор
  сохраняется при перезагрузке; на 360px не едет вбок.
Ветка: feature/journal-sorting · влито 2026-08-31.
```

Пиши так, чтобы заказчик увидел свой пункт своими словами и понял, во что он превратился.

## Грабли

- **Не создавай файлы на Drive** — 403, см. выше. Только папки и правка чужих файлов.
- **`push` затирает документ целиком.** Сначала `pull`, потом правь, потом `push` — иначе
  потеряешь то, что человек дописал руками.
- **Разделитель в именах папок — ` · `.** В названии задачи его быть не должно, иначе разбор
  съедет. `add` этого не проверяет.
- **Статус `готово` ставится после слияния в `develop`**, а не после того, как код написан:
  «сделано» и «принято» — разные вещи.
